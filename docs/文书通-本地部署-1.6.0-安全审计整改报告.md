## 1. 送审范围

本次复审对象是**内网本地部署安装包**，不是 Microsoft Store 或 Mac App Store 上架包。

原审计包（SHA256 `666d6183…`）是整改前的产物。本次送审样品是 2026-09-24 在 Windows 10（10.0.19042）上重新构建的本地部署 NSIS 包，SHA256 为 `9b02b20a0366aa79054fd096c3ba313e9262fd7caa1c8985ad344b5ae28161a5`。两份文件同名，必须以哈希区分。审查单位若对旧哈希复测，高危项仍会复现。

本地部署的使用条件，作为残留风险的补偿控制，建议写入部署说明并请使用单位确认：

1. 安装介质由使用单位在内网保管，不从公网下载。
2. 安装前核对交付方提供的 SHA256，与介质不一致则不安装。
3. 模型地址只配置本机或内网地址。产品在 local 档位下会拒绝公网域名和公网 IP。
4. 终端不出公网，或由使用单位防火墙限制该软件出站。
5. 技能包只安装本单位审核过的脚本。

Microsoft Store、Mac App Store 的平台签名只覆盖各自上架的那一个包。不能写入本报告作为本地部署 NSIS 包已签名的依据。审查员对送审的 `setup.exe` 做签名检查时，该项仍为未签名。

## 4. 高危项（复审重点）

### 4.1 H-01 鉴权与档位

原问题：只有启动器注入令牌时才校验；`/shutdown` 不校验；直接运行运行时可读配置、改模型地址，并把档位降为 standard。

整改：

- 未注入令牌时，运行时自行生成令牌，不写入日志。除 `/health` 外都要带 Bearer。`/shutdown` 同样校验。
- 部署档位以安装包内的 `deployment-profile` 为准。环境变量只能把 standard 收紧为 local，不能把 local 降为 standard。
- local 档位拒绝公网域名和公网 IP 作为模型地址。监听非回环地址时，必须由调用方事先提供令牌，不能用运行时自己生成的令牌。

证据：macOS 上运行时测试 331 项通过，其中包含鉴权拒绝、档位不能降级、公网 IP 被拒绝。2026-09-24 在 Windows 10（10.0.19042）上重跑 `test_auth.py`、`test_deployment.py`、`test_main_cli.py`、`test_gateway.py` 与 `test_app_api.py` 中的对应用例，结论相同：不带令牌访问受保护接口返回 401，`/health` 除外；local 档位不能被环境变量降级，公网域名和公网 IP 被拒绝。这次是源码测试，不是对安装包里的 `desktop.exe` 双击启动。

未按原文实现的部分：不用调用进程身份作为 `/chat` 的第二因素。本机 HTTP 看不出可靠的对端进程，界面进程和运行时本来就是两个进程。同一 Windows 用户若已能调试该用户的全部进程，也可以读到令牌。这项不承诺挡住已控制该用户会话的程序。原报告描述的「双击运行时，接口完全开放」已经关闭。

### 4.2 H-02 脚本隔离

原问题：Windows 上缺少隔离工具时仍然执行脚本，进程内补丁只盖住 `builtins.open`。

整改：

- Linux 使用网络命名空间，macOS 使用 `sandbox-exec`，Windows 使用不授予网络能力的 AppContainer，并挂上 Job Object，主进程结束时脚本进程一并结束。
- 隔离创建失败则拒绝执行，不再因为平台是 Windows 而放行。
- 技能脚本和共享脚本始终隔离。可写范围为工作区、技能目录、共享脚本目录和单独的 `skills_state.json`。`config.json` 不在可写范围。
- 进程内再限制 `io.open`、`os.open` 和删除、改名，并替换 `subprocess`、`ctypes`、`socket` 的入口。

证据：macOS 隔离进程可以更新技能状态、不能写配置文件；技能安装端到端测试通过。

Windows 抽测（2026-09-24，Windows 10 10.0.19042，源码，不是安装包）：

第一次按 `7ce11f6` 实跑时，技能脚本起不来。`CreateProcessW` 返回错误 203，因为宽字符环境块没有带 `CREATE_UNICODE_ENVIRONMENT`。进程被拒绝，配置文件没有被改写，但脚本功能本身不可用。补上该标志后，AppContainer 仍读不到、也执行不了虚拟环境指向的 Python，随后又因 `PYTHONPATH` 未授权而导入失败。这些都已在 `3b86fb9` 修改：创建进程使用 Unicode 环境，解释器目录授予读取和执行，`PYTHONPATH` 只读。`config.json` 仍不在可写范围。

`3b86fb9` 之后在同一台机器上经产品路径 `run_skill_script` 实跑：

- 工作区标记文件写成，标准输出含 `ws=ok`。
- 写 `config.json` 得到 `PermissionError`，文件内容保持原样。
- 连接 `1.1.1.1:443` 得到 `PermissionError`。这是产品路径上的结果：AppContainer 未授予网络能力，进程内又替换了 `socket`。
- 将 AppContainer 接口标为不可用时，调用被拒绝，脚本没有执行。

对应回归：`test_run_skill_script_allows_skill_dir_argv`、`test_run_shared_script_allows_shared_dir_argv`、`test_run_workspace_script_allows_in_workspace_argv` 通过。

技能仍须能运行。隔离的是进程权限和网络，不是关闭脚本功能。新安装包里的同一行为尚未用打包后的运行时再测一次。

## 5. 中低危与补偿控制

### 5.1 M-01 未签名（残留，建议风险接受）

本地部署包不购买 Authenticode 证书。送审材料应直接写「未签名」，并给出使用单位可以执行的补偿措施：

- 介质不经公网，由交付方交给使用单位。
- 随介质提供 SHA256，安装前核对。
- 安装后的程序哈希可与交付清单比对。

这样写，审查员能够复核。若写成「已获得商店签名资质，故本安装包符合签名要求」，对这个 NSIS 文件的签名检查会失败，材料会被退回。商店上架与本次送审对象不是同一个文件。

未签名的剩余影响是：Windows 可能提示未知发布者；介质若在交付后被替换，操作系统不会用签名拦截。补偿措施靠的是交付保管和哈希，不靠 SmartScreen。

### 5.2 M-03 固定版浏览器组件

新构建将 WebView2 固定版从 `133.0.3065.92` 改为 `151.0.4129.107`。2026-09-24 这次打包使用的目录是 `apps/desktop/src-tauri/webview2-runtime/Microsoft.WebView2.FixedVersionRuntime.151.0.4129.107.x64`。打出的 `desktop.exe` 内含字符串 `151.0.4129.107`，不含 `133.0.3065.92`。安装包本体是压缩过的 NSIS，对 `setup.exe` 做明文检索看不到该版本号。

不启用自动更新，也不改用跟随系统更新的常青版。本地部署要求内网可断公网。自动更新会让已安装软件自行连接外网，这与送审环境的出站限制冲突。漏洞修复方式是使用单位更换新的安装包。旧哈希 `666d6183…` 那个包里的 133 版本不在本次送审样品中。

### 5.3 其余项

- M-04：技能安装改为导入白名单，未列出的模块拒绝安装，其中包括 `subprocess`、`ctypes`、`socket`、`urllib`、`winreg`。`--force` 不能跳过校验错误。不再为每个技能单独做一套权限裁剪，执行边界由第 4.2 节的进程隔离承担。
- M-05：产品调用脚本时先做路径根目录检查，再进入隔离进程。有人用系统 Python 自行运行某个脚本文件时，产品不再介入，此时权限就是该用户本来的权限。
- M-02：生产界面策略已去掉 `ws://127.0.0.1:1420`、`ws://localhost:1420`、`1421`。对本包 `desktop.exe` 检索：上述 WebSocket 地址和 `1421` 均未出现，`{{product_name}}` 未出现。仍有一处 `http://localhost:1420`，来自 `tauri.conf.json` 的 `devUrl`，不是连接策略里的放行项。旧包中的构建机路径必须用本包重新提取后才能关闭，本次没有做完整字符串提取。
- M-06：构建按实际环境生成 CycloneDX 物料清单，并写入 WebView2 再分发说明。这是许可与供应链台账，不构成可利用漏洞。约 29 个组件的许可全文尚未逐份归档，新包应附带当次清单。
- L-01：端口仍为 `127.0.0.1:8765`，便于界面和内容安全策略固定连接目标。无令牌的进程不能通过 `/shutdown` 关掉占用者；回收后端口仍被占用则外壳退出，避免连到未知服务。令牌仍经环境变量交给运行时。已能调试该用户进程的程序不在防护承诺内。
- L-02：已与 H-01 一并关闭。
- L-03：两条打开旧版 Word 文档的路径都在打开前把 `AutomationSecurity` 设为 3。2026-09-24 在本机 Word 16.0.19127 上用带 `AutoOpen` 宏的 `.doc` 复核：宏会在磁盘写出标记文件。走产品转换路径时，本机没有 `pywin32`，实际执行的是 PowerShell 调用 Word 的那一条；转换得到 `.docx`，标记文件没有出现。同一份文档以 `AutomationSecurity = 1` 打开时，标记文件出现。pywin32 那一条代码同样在打开前设为 3，这次没有走到。
